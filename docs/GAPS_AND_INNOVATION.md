Content for `CollegeName_TeamName_Submission.pptx`, organised by slide. Take every number from `metrics.md`; they are regenerated by `python eval/run_metrics.py`.

## Slide 2: Theme
**Theme 2: Smart Guided Troubleshooting Engine.** It turns vague Galaxy complaints ("screen flashes and goes blank when I open Gmail") into validated, ordered, one-tap Settings plans with masked Bixby deeplinks. Target: under 300 ms for known issues, replacing a manual triage of about 15 minutes per ticket.

## Slide 3: Existing solutions and gaps

**Today (per the brief):** an agent reads SIIS articles, picks the steps, orders them and types instructions. The customer then navigates nested menus by hand.

**Gaps in the brief itself**
1. `validationDeeplink` is in the schema but has no filling rule, so nothing proves a fix worked.
2. There is no abstain threshold: "return empty when no viable solution" is never defined, and retrieval always returns something.
3. The pipeline assumes a single intent, yet kit query #17 contains three complaints.
4. The cache can be poisoned: a wrong plan gets replayed to every paraphrase.
5. Destructive steps are only "ordered last". There is no backup-first rule and no gating.
6. "Derive only from the reference" is not checkable from the output, because no provenance is required.
7. On/off twin deeplinks exist for the same switch, but direction selection is never mentioned.
8. Appendix C has no gold labels, so teams end up grading themselves.

**Gaps in the starting engine (v1)**
- Titles were cut to three words ("Some things to", "Blank or black").
- Descriptions were padded ("It will overview settings settings").
- "Overview" and "What is casting" became actions.
- Generic steps got random screens: "Charge the device" → Connected devices.
- A factory reset was marked **auto**.
- Score was always about 0.93.
- Paraphrases were garbled, giving a 0% hit rate on real paraphrases.
- The cache was pre-warmed with the evaluation queries, so the "cold" numbers were really cache hits.
- A script could overwrite the official kit.

## Slide 4: Our solution and architecture
Enrichment → semantic cache → SIIS retrieval with a relevance gate → extraction (steps are imperative and atomic, one screen per action, provenance kept) → deeplink mapping (verbatim setting name → TF-IDF over descriptions → twin direction → `dummy_positive` only for real Settings paths) → validators (field rules, URL scrub, category rules, ordering) → REST → **closed-loop verification**. An optional Groq LLM drafts the structure; its output is always re-grounded and re-validated.

## Slide 5: Demo
Console at `web/`, with four pages:
1. **Troubleshoot**: pick a kit complaint → plan in tiers → *Run safe steps* → the phone simulator opens each screen, flips the switch and shows "Fix confirmed". The last-resort tier stays locked until you click *Problem still there*.
2. **Trace**: hover a step to highlight the exact SIIS sentence it came from. Also shows stage timings, retrieval candidates and mapping reasons.
3. **Batch run**: all 20 `input.txt` complaints, with a download of `results.jsonl`.
4. **Metrics**: before/after comparison and the ablation.

Edge cases to show:
- The compound complaint produces three Goals.
- The infrared-blaster query returns an empty plan with `no_siis_context`.
- "s22 touch input delay laggy screen" is served as a cache hit.

- Optional Groq (llama-3.3-70b / 3.1-8b) through the OpenAI-compatible client.

## Slide 7: Impact and use case
- Replaces about 15 minutes of manual triage per ticket with sub-second plans. Cache hits cost $0.
- A one-tap deeplink per auto step, and **confirmation** that the setting actually changed. Fewer unnecessary factory resets and service visits, because disruptive steps unlock only after the safe ones fail.
- Every step can be audited back to the source sentence, which answers the compliance question "did the bot invent this?".

## Slide 8: Innovation, results and limitations
**Innovation:** closed-loop verification.
- `validationDeeplink` is derived from the catalog twin.
- The on-device agent (simulated) taps the fix, reads it back via the `val/` URI, and escalates only if the fix is confirmed but the problem remains.
- Supporting pieces: provenance spans, a relevance gate with a calibrated score, multi-intent Goals, a cache-poisoning guard, backup-before-destructive (as in the official sample output).

**Results:** see the metrics.md before/after table.
- Rule compliance: 5% → 100%.
- Deeplink relevance: 0.03 → 2.0.
- Paraphrase cache hits: 0% → 90%.
- Zero URL leaks.
- 100% catalog-valid URIs.
- Cold P95 in tens of ms (deterministic path).

**Limitations**
- Several kit queries are paired with only loosely related articles (floating circle → Multi window).
- The catalog lacks Safe mode, Software update, Apps › Storage, Auto rotate and Assistant menu.
- The deterministic extractor is tuned on the 11 distinct kit articles; the Groq path is the intended generaliser.
- The simulator is a mock, not a real device.

## Slide 9: What's next
- Real on-device verification through Bixby / Galaxy Settings intents.
- Learning plan ranking from verified outcomes: which fix actually resolved the ticket.
- Multilingual and Hinglish complaints.
- Per-device screen variants (Flip cover versus inner display).
- Dense multilingual embeddings for the cache, with the same symptom gate.

## Slide 10: Differentiation
- We **measure** what we claim, using an independent scorer with hand-labelled gold and 60 unseen paraphrases, run against the old engine as well.
- A fix is **verified**, not just linked.
- No step is invented: every step traces back to a source sentence.
- It runs with zero API keys; the LLM is optional and fenced.
